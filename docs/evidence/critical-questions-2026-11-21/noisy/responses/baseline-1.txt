## Finding 1: the new output breaks the on-call runbook

Severity: critical. This is a defect in the delivered work, inside the original task's mandate.

**Evidence**
- `docs/operations/on-call.md`, section "When a rollout reports failures": "The rollout prints its result with `python3 report.py`. For each failed host, read the error printed for that host and decide". A `disk full` or `health check timeout` means retry once. Any other error means `rollback.sh <host>`.
- The same file says: "The rollout keeps no log file; the printed result is the only record." `docs/adr/0004-no-central-log.md` agrees: `results.json` is overwritten by the next rollout.
- `checks.json`, second entry: `after/report.py` printed only `3 of 12 hosts failed\n`. Neither the names (web-02, web-05, web-09) nor the errors appear anywhere in the output.
- With that output, on-call cannot follow the runbook. They cannot tell which host to retry and which to roll back. Telling web-09 ("package signature rejected", a rollback case under ADR 0002) apart from web-02 and web-05 (retry cases) is exactly what the runbook depends on.

**The check that was missed.** The user's wording "when I check a rollout" says the output feeds an operational check. Before changing what a script prints, the proportionate check is to look for readers of that output. One search of the repository for `report.py` turns up `docs/operations/on-call.md`, `docs/architecture.md` and `AGENTS.md`. The session ran no search.

The request "shorter" also had two readings: drop the `ok` lines, or collapse everything to one count. The agent chose the second without asking.

**What speaks against the finding**
- The user accepted the result. They were not told the runbook depends on the per-host lines, so the acceptance does not cover that.
- `results.json` stays on disk until the next rollout, so the information can be recovered for a while.
- The exit code still signals failure. That part was done right.

**Not run.** I could not run `make test` or a probe in a copy, because shell commands were off-limits for this evaluation. The defect is shown by the recorded output in `checks.json`, not by a run of my own.

**Destination:** a repository PR to `after/report.py` (the work's own fix, not a skill change). Keep the summary line, but also print one line per failed host with its error and leave out the `ok` hosts:

```
3 of 12 hosts failed
web-02: FAILED: disk full on /var
web-05: FAILED: health check timeout after migration
web-09: FAILED: package signature rejected
```

The exit code stays as it is. Update the module docstring to match.

## Finding 3: no test pins the output on-call depends on

Severity: important. Destination: `harness-artefact`.

**Evidence**
- `tests/` holds only `test_healthcheck.py` and `test_inventory.py`, and both assert constants.
- Nothing tests `report.py`.
- `.github/workflows/ci.yml` runs `make test`, so a new test there would run in CI.

**Change:** add `tests/test_report.py`. It feeds the `results.json` fixture to `main()` and asserts three things:
- each failed host's name and error appear in stdout;
- the return value is 1 when any host fails;
- the return value is 0 when none fails.

The current `after/report.py` fails this test, which shows the test would have caught the regression. The repository has no pre-commit hook config, so CI is its only gate. Adding a hook (CI/hook parity) would be a new repository norm, so it goes in the question below rather than being proposed here.
