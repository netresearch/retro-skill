### Finding 1: the documented test and lint gate is not wired into CI (`harness-artefact`, important)

- **Claim and kind:** This is an observation and a verified fact. `AGENTS.md` says "Run `make test` and `make lint` before pushing". `.github/workflows/build.yml` runs on `push` and has one job, `image`, whose only step is `docker build -t signup .`. Neither documented command runs in CI. A push made without the manual step, by a human or by an agent that skips the line, reaches the remote untested.
- **Evidence:** `inputs/AGENTS.md`, `inputs/.github/workflows/build.yml` and `inputs/Makefile`. `inputs/checks.json` shows that both commands exit 0 on the session's tree.
- **Why this session:** The agent did follow the rule ([05], [06]), and that is the Glad line below. But the user's next step is "ship it", and at that point nothing on the server checks the change. The skill's harness-inspection text describes this exact case: "a gate described as a list is a gate whose last two steps get skipped." I did not see a skipped run happen. The consequence is that the next push gets no test or lint run.
- **Purpose check:** The rule protects real quality: the validation tests are the only check on the requested behaviour. Keep it and enforce it. Do not remove it.
- **Proposed change:** Extend `build.yml`; do not replace it.
  - Add a `test` job with `actions/checkout` (SHA-pinned, since it is a third-party action) and then `make test` and `make lint`.
  - Add job-level `permissions: contents: read`, because the workflow sets `permissions: {}` and checkout needs read access.
  - Optionally add `pull_request` to `on:`.
- **CI/hook parity:** Both commands meet the fast-check definition as measured: deterministic, no external dependencies, and `Ran 3 tests in 0.000s`. `py_compile` clearly qualifies. I am treating `make test` as fast because it measurably is, not as a "full test suite" exception. Under `patch-workflow.md` § CI/hook parity, the same commands must go into a pre-commit hook in the same PR.
  - None of the seven input files is a hook config (no lefthook, pre-commit or husky), so the hook would be a new bootstrap, not an extension.
  - Bringing in a hook framework is the repo owner's decision, so it is in the question below.
- **Routing:** This is a plain `harness-artefact` with no `skill-update` paired to it. There is no evidence of sibling repos with the same gap, and skill discovery could not run (see deviations), so I cannot show a skill that lacks an install recipe.
- **Precondition:** Wiring in existing commands adds no rule. It needs only that they pass on the base branch. They pass on the session's tree. The base branch is not in the record.
- **What would confirm the benefit:** The first push after the merge shows a `test` job that runs both commands. A deliberately broken test makes that job red. Until that happens, the effect is untested.
