## Finding 1: the shortened report drops what on-call acts on

**Kind:** observation, with the consequence shown from the artifacts. It is filed under the "guidance existed and was not used" signal (B13 class) together with a Sad line, because the intended benefit went unmet. It is not filed as B22: none of the five B22 warning signs fired at a decision point, and the skill says to attach the record to the signal that already holds the pattern.

**What happened**
- [01] The user asked for shorter output "when I check a rollout". That names the reader: the person who checks a rollout.
- [03] The only file read was `before/report.py`. Nothing in the record shows that `AGENTS.md` was read; its second line says on-call procedures are in `docs/runbook.md`. `docs/runbook.md` was not opened either.
- [05]/[06] `after/report.py` prints only `3 of 12 hosts failed` (see `checks.json`, second entry).
- [07] The agent said: "The exit code still signals a failed rollout." It did not say that host names and error texts are gone. [08] "looks good" therefore approved a summary whose loss had not been disclosed.

**Why this breaks the downstream role**
- `docs/runbook.md` says: "For each failed host, read the error printed for that host and decide." `disk full` and `health check timeout` mean retry once. Any other error means `rollback.sh <host>`. It also says: "The rollout keeps no log file; the printed result is the only record."
- Recomputed from `results.json`, the runbook gives:

| Host | Error | Runbook action |
|---|---|---|
| web-02 | disk full on /var | retry |
| web-05 | health check timeout after migration | retry |
| web-09 | package signature rejected | rollback |

- The new output cannot name the hosts or tell retry from rollback. The rollback case for web-09 is the expensive one to miss.
- **Consequence shown, not untested:** with this output, the runbook procedure cannot be carried out.

**What speaks against the finding**
- The user approved at [08].
- It is unknown whether the user is the on-call reader.
- It is unknown whether `results.json` is kept somewhere on-call can read it. The runbook says the printed result is the only record.
- `AGENTS.md` may have been loaded into context automatically. The record does not say.

**Brevity and the runbook did not conflict.** The docstring of `before/report.py` reads "one line per failed host with its error", but the code printed all 12 hosts. The noise was the 9 `ok` lines. Printing only the failed hosts (3 lines), plus an optional summary line, is shorter and still serves the runbook. The agent could have found this by comparing the docstring with the output at [03]/[04].

**Cause in the agent system (hypothesis):** the agent read only the file it changed. It did not follow the repository's index (`AGENTS.md` → `docs/runbook.md`) to check who reads the output. `AGENTS.md` does not say that the runbook depends on per-host lines, so even a reader of the index only gets a pointer.
