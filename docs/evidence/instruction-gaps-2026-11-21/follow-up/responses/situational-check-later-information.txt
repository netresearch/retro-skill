# Retro report: outcome review of the date-parsing session (`/retro outcome`)

**Result: no finding against the original session's decision.** The narrow fix for DD.MM.YYYY was justified by what the session could know. The later YYYY/MM/DD failure is an Outcome-mode signal (D6, a requirement that grew after the session). It is not a missed situational check (B22), and nothing in the skill or the rules needs to change because of it.

## The decision point

**Decision:** the fix handled exactly the one format the ticket listed (DD.MM.YYYY), and a test covered it.

**What the session knew at that moment:**
- The ticket named one format.
- The session held no sample, log or message that mentioned any other format.

**Check against the B22 warning-sign table** (`friction-catalog.md` § Missed situational check). None of the five signs was visible:
- No observation contradicted the working explanation.
- No failure class came back in a variant during the session.
- No special handling for one format spread across layers.
- No new case needed another exception or a workaround.
- No large restructuring started from one isolated case.

**Outcome category: "Not needed".** The skill defines this as "the information at that point justified the narrow step". It produces no finding.

**Hindsight rule applied.** The skill says: "Judge by what was knowable then. A case that appeared only later does not condemn the earlier fix; it may be a D signal in Outcome mode." The YYYY/MM/DD file arrived three days after the session, so it cannot make the earlier decision an omission.

**What speaks against this verdict:**
- B12 (an assumption made instead of asking) would apply only if the scope was ambiguous at the time. The ticket listed the format explicitly and nothing in the session suggested other formats, so there was nothing to ask about.
- **ASSUMPTION:** I take "the one format the ticket listed" to mean the ticket scoped the work to that format. If the ticket instead said "date parsing fails" and cited DD.MM.YYYY only as one example, the session narrowed the scope itself. That would still not be a B22 finding, because no warning sign is described. It could be a B12 candidate, and only the ticket text settles it.

## The later event, classified

**D6, issue or ticket feedback after the session.** A new ticket was opened three days later. The skill says to read the cause before treating such feedback as a fault of the session. As described, the cause is an input class nobody had seen before. That is a requirement that grew, not a defect the session introduced.

**Not B19.** B19 covers a defect that review, CI or QA found in the delivered change. Here the delivered change did what it was meant to do. The new failure lies outside its specification.

**This classification rests on one unknown.** It decides between "requirement grew" and a real defect: did YYYY/MM/DD files parse before the session's fix?
- If they failed before as well, the D6 reading stands and nothing more is needed.
- If they parsed before and fail since the fix, the fix broke them. That is a regression (close to D8) and a real adverse outcome. It would also be a B19-type gap: the test covered only the new format and kept no characterization test for formats that already worked.
- What settles it: run the YYYY/MM/DD input against the commit before the fix and against the fix commit, and compare the results.
