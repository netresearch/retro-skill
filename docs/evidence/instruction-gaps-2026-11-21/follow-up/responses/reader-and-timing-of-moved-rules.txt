# Retro report: `/retro promote` with a request to slim the always-loaded `AGENTS.md`

## How the request is handled

The skill says a request to slim `<project>/AGENTS.md` is not a scan. The scanner skips `AGENTS.md` on purpose (promote-mode.md, "What the scanner reads (and excludes)"). So Phases 1 to 3 do not run. I applied the three rules from "Draining the global rules file" to the sections by hand. For each part that moves, I name which agent reads the destination and what triggers that read.

Mandate: the user asked to slim `AGENTS.md`. That covers editing `AGENTS.md` and moving its content to another document inside the same repository's rule store. destination-taxonomy.md §2 says a document "that a configured agent loads (a review guide its review agent reads)" is part of that store, so the move is still a `project-rule`. Both files are committed in the same repository, so the content reaches no new audience and no disclosure question comes up (Risk control 2).

## Finding 1: move the ~120 lines of review heuristics to `docs/review-guide.md`

**Evidence:** about 120 of the 300 lines are review heuristics: naming, comment style and readability checks. The repository's review agent applies them to diffs. The review agent is configured to load `docs/review-guide.md` for every review.

**Rule check:**
- **Rule 1 (always-on behaviour stays):** these are not rules that must hold in every turn. They are not bans, tone rules or verification discipline. They are conventions applied when a diff is judged.
- **Rule 2, generalization:** the heuristics apply to every contributor and every agent working in the repository, not only to this user.
- **Rule 2, safe to lose from always-loaded context:** the reader who needs them is the review agent. It loads `docs/review-guide.md` reliably before the decision these heuristics govern, which is the review of the diff. Rule 2 also says that "a convention a reviewer can still correct in the diff can" move. Naming, comment style and readability are exactly that kind of convention.

**Reader and timing:**
- Reader: the repository's review agent.
- Trigger: every review, through its configuration that loads `docs/review-guide.md`.
- Cost: the agent that writes code no longer sees these heuristics in every turn. A violation is then caught one review round later instead of avoided. That trade is acceptable for conventions the reviewer can correct.

**Destination and change:** a `project-rule` that moves content inside the repository's store.
1. Append the heuristics to `docs/review-guide.md`.
2. Before appending, read the guide and compare mechanisms, not titles (paraphrase dedup). A heuristic the guide already covers is only removed from `AGENTS.md`, not appended twice. Name the guide section that covers it.
3. Optionally, keep a one-line pointer in `AGENTS.md` ("Review heuristics: `docs/review-guide.md`"). That keeps the guide easy to find for code-writing agents that want to apply the heuristics early.

**Checks before removing anything from `AGENTS.md`:**
- **Read the review agent's configuration itself.** Confirm that it loads `docs/review-guide.md` for every review. Do not rely on the description of that configuration. Also note which ref it loads the guide from: the default branch, or the head of the PR.
- **Classify each of the 120 lines one by one, not as a block.** A line that only looks like a readability rule but constrains code before it is written (for example "never log personal data", or an API-usage rule) fails rule 2 and stays.
- **Availability:** the moved text counts as available only when it is on the branch the review agent reads. An open PR is preparation, not availability.

**Order of work (rule 3, Phase 9):**
1. Write to `docs/review-guide.md` first and read it back.
2. Verify availability as above.
3. Only then remove the sections from `AGENTS.md`, one section per edit.
4. Hash each section when you read it, and compare that hash with the section's current text immediately before removing it.
5. Remove sections fence-aware: a `#` comment line inside a code fence is not a section heading.
6. Afterwards, check that the fences are balanced and that the section count dropped by exactly the number of sections removed.

If both files change in one branch, they are delivered together at merge. That merge is the moment the moved text becomes available. Make sure the slimmed `AGENTS.md` cannot land before the guide change.

## Finding 2: the `tenant_id` rule stays in `AGENTS.md` (a justified non-move)

**Evidence:** one section states that every database query must filter by `tenant_id`.

**Rule check:** this is a data-isolation constraint. It must hold before code is written. Rule 2 names this case: "A rule that must hold before code is written, such as an architecture or data-isolation constraint, does not move to a file read only at review." If it moved to the review guide, the code-writing agent would no longer see it while writing queries. A missed filter is a tenant data leak, not a style point. Rule 1 also says that when in doubt, the section stays.

**Destination and change:** none. The section stays unchanged.

**Possible gate, not counted as a proposal:** Axis 1 and rule 1 allow pairing a rule like this with a mechanical gate while the prose stays. Examples are a static check or a test that rejects queries without a `tenant_id` filter. I could not calibrate such a gate here: there is no codebase and no corpus, so I cannot say how often it would fire or what it must not fire on. An uncalibrated tier-1 proposal is weaker than leaving it out. The repository owner decides whether a gate is worth building.
