### How the request was read

`/retro promote` excludes `<project>/AGENTS.md` from its scan by construction. A request to slim it is "no scan": the three binding rules are applied to its sections by hand, and for each moved part the report names which agent reads the destination and what triggers that read (promote-mode.md, "What the scanner reads").

The request can be read two ways:
- **Reading 1:** slim `AGENTS.md` only.
- **Reading 2:** a default promote, which also scans the memory stores and the global rules file, plus the `AGENTS.md` slimming.

This report covers Reading 1. Question for the user: should the default memory and global-rules scan run as well?

### Finding 1: review heuristics (about 120 lines). Move, after verification

- **Evidence (from the task description):** these lines are review heuristics covering naming, comment style and readability checks. The repository's review agent applies them to diffs. `docs/review-guide.md` exists, and the review agent is configured to load it for every review.
- **Two-direction test (rule 2):**
  - *Generalizes:* yes. This is already team content in a committed repository file. The move goes from one team file to another in the same repository, so it reaches no new audience.
  - *Safe to lose from always-loaded context:* the reader is the review agent. The trigger is the configured load at the start of every review. That makes it a reliable load before the decision these lines govern, which is judging a diff.
- **Limit from rule 2:** "A constraint the implementer needs while designing does not move to a file read only at review." Readability checks are judged at review time, so they move. Naming and comment style are partly applied while the code is written. If they leave always-loaded context, the cost is extra review rounds, not a safety failure. Rule 1 still says "when in doubt, the section stays."
  - Proposal: move the pure review-time checks.
  - Decision for the user (or the repository's owners, because it is a team norm): do the naming and comment-style conventions also move, or does `AGENTS.md` keep a short version of them? A pointer sentence alone is not a reliable load for the implementer.
  - Cheaper option, not verified: if the repository already runs a linter, a naming rule there would enforce this for everyone (harness-artefact, project-harness-inspection.md). Whether such a linter exists is unknown.
- **Checks before materializing (not run here; each is a precondition):**
  1. Read the review agent's configuration and one recent review run. This confirms that `docs/review-guide.md` is actually loaded, and from which ref: the PR head or the default branch. "Configured to load" is the declaration; it is not proof that the file is read.
  2. Paraphrase dedup: read `docs/review-guide.md` and compare mechanisms. Only the parts the guide does not already cover are appended. Covered lines are simply removed from `AGENTS.md`, with the covering location cited (Instruction pruning).
  3. Confirm that the review agent does not get these heuristics only from `AGENTS.md`, for example because it never loads the guide in some path.
- **Destination and change:** append the uncovered heuristics to `docs/review-guide.md`, then remove them from `AGENTS.md` in the same PR. This ordering holds only if the review agent reads the guide from the PR head. If it reads from the default branch, removing the lines from `AGENTS.md` waits until the guide change is merged and available. Section removal must be fence-aware. Afterwards, check that fences are balanced and that the section count dropped by exactly the number removed.

### Phase 11 self-check: proposed changes to retro-skill (at most two)

1. **Missing race check on the by-hand path.** Rule 3 requires re-checking the scan's `content_sha256` before removing a section. A by-hand `AGENTS.md` slimming has no scan, so it has no hash. The instructions name no substitute, such as recording the blob SHA or a section hash at the start and re-checking it before the edit. I propose adding one to promote-mode.md, in the "Excluded by construction" paragraph.
2. **Rule 2's first condition is phrased for the personal file.** "Generalizes beyond this user" was written for the global rules file. For `AGENTS.md`, which is already team content, the condition is always true. That leaves the reader-timing half as the only real test without saying so. I propose wording this for the `AGENTS.md` case.
