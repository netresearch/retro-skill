## Finding 1: a documented gate that nothing enforces

**Signal:** project-harness inspection, row "One-command entry points / CI workflows". The question that row asks is: "Did the session run a documented sequence by hand? A gate described as a list is a gate whose last two steps get skipped." This session did exactly that. It is the same shape the inspection reference cites as its founding case: "a documented six-suite pre-push gate that existed only as a list to execute by hand."

**Claim and kind:** a verified fact about the harness, plus a hypothesis about the risk.

**Evidence** (all from the task description; I read no repository file):
- `AGENTS.md`: "run make test and make lint before pushing".
- `.github/workflows/build.yml` is the only CI workflow. It builds the image and runs neither target.
- No hook configuration exists in the repository.
- The agent ran both targets by hand, and both passed.

**What speaks against it:**
- No failure happened, so the expected benefit is untested.
- CI may have had a reason not to run tests, for example tests that need services the runner lacks, or an earlier decision to drop them. Unknown.
- Whether branch protection requires any check is unknown.

**Purpose check (Axis 1):** the rule protects code quality before a push, the user's own repository states it, and the agent followed it without conflict. It is valid and not redundant. Only its enforcement is missing.

**Authority (Axis 0):** this is not a fact about the world with an outside owner. It is a rule of the repository itself, so `canonical-source` does not apply.

**Enforceability (Axis 1, tier 1):** both rules are exit codes of `make` targets, so a mechanical gate is available. A CI step fails whenever either target fails.

**Destination:** `harness-artefact` in the service repository the session worked in. It stays a plain artefact, not a pair: I could not run skill discovery (see the deviations), so I cannot show that a skill should carry an install recipe. Inventing that second half is not allowed.

**How to apply:**
1. **Read the history first.** Run `git log -S 'make test' -- .github/workflows` and `git log -S 'make lint' -- .github/workflows`. If an earlier commit removed these steps on purpose, read that decision before reversing it.
2. **Extend `build.yml`, do not replace it.** Add a job or steps that run `make lint` and `make test` on `pull_request` and `push`. The image build stays as it is.
3. **Check that `make test` can run on the CI runner.** Run it once in CI or a clean container to find out whether it needs a database or another service. If it does, prepare that service in the job.
4. **Decide the hook parity by measurement.**
   - `make test` is a full test suite, so CI alone is complete. A pre-push hook is optional.
   - `make lint` needs parity only if it counts as a fast check: deterministic, under about 5 seconds, no external dependencies. Time it.
   - If it is fast, the same command goes into a pre-commit hook in the same PR. Because no hook config exists, that is a bootstrap through `agent-harness-skill`. Which hook manager to use is the team's choice.
   - If it is not fast, CI alone is complete, and the PR body says why there is no hook.
5. **Make the job block merges (manual, not applied).** A CI job blocks a merge only if it is a required status check. Without branch-protection access I would prepare the `gh api … /branches/<default>/protection` specification and mark that row `manual`.
6. **Leave `AGENTS.md` unchanged.** The sentence there is still useful as local guidance. Optionally, add one line saying CI now enforces both targets.

**Expected behaviour after the change:** a push or PR that fails `make test` or `make lint` turns CI red and, if the job is required, blocks the merge. The first PR whose CI fails on these steps confirms the benefit. Until then it stays untested.

## Contradictions in the instructions

1. **A green session and the tier-1 test.** The classification heuristic tests a gate by "whether a check could have *failed* on the friction as it actually occurred". The linter rule in `patch-workflow.md` §5 says a rule must fire "on the friction as it occurred". But the Sweep says a smooth session still owes its findings, and the harness-inspection reference cites a hand-run gate list as a qualifying finding with no failure attached. In a session with no friction, the test has nothing to test against.
   - I read it as: the check must be able to fail on the defect class the rule guards. A failing `make test` or `make lint` turns CI red.
   - A single sentence in `classification-heuristic.md` covering latent gaps would remove the ambiguity.
2. **Parity, two wordings.** `destination-taxonomy.md` says "every fast, deterministic check in CI must also run as a pre-commit hook". The harness-inspection reference says "A hook config … almost never absent outright … Extend it". Here no hook config exists, so parity means bootstrapping a new one, which the texts treat as the exception.
   - This is not strictly a contradiction, because verify-before-bootstrap does allow a bootstrap when the artefact is truly missing.
   - Neither text says who chooses the hook manager when none exists. I left that choice to the team.
